# Database design

PostgreSQL 16 is the system of record. P001 migration `0001_baseline` creates no domain tables. The schema in this document is the target for later phases. Treat a table as real only after an Alembic revision creates it.

Redis is not a system of record. It is the Celery broker. Later short-lived coordination may use it. Orders and payments are never stored only in Redis.

## Conventions

- Primary keys are UUIDs generated by the database.
- Timestamps are `timestamptz` and stored in UTC.
- Operational rows include `canteen_id` even while the pilot has one canteen.
- Money columns are `bigint` paise. Names end in `_paise`. They are not `float`, `double precision`, or unscaled `numeric`.
- Status columns are text with a check constraint that matches the documented states.
- Updates that change an order or a payment also insert an event row in the same transaction.
- Foreign keys are indexed. The column that is filtered most often in a composite key comes first.

## Transaction boundaries

Each boundary is one database transaction. The service commits once at the end. A failure rolls the whole boundary back.

| Boundary | Writes | Must not do |
| --- | --- | --- |
| Place order | Order, items, PENDING payment, PLACED event, stock reservation | Mark PAID or PICKED_UP |
| Fulfillment transition | Order status, version, fulfillment event | Touch payment status |
| Cash receipt | Payment PENDING to PAID, payment event, audit | Set PICKED_UP or notification status |
| Pickup | Order READY to PICKED_UP, token consumed, fulfillment event, audit | Change the amount or create the payment |
| Void | Payment PAID to VOIDED, payment event, audit | Delete the PAID event or rewrite a PICKED_UP order into READY |
| Staff change | Assignment and audit | Modify orders |
| Notification attempt | Notification row only | Modify order or payment |

Readiness probes (`SELECT 1`, `PING`) are not domain transactions.

## Concurrency

Order and payment rows carry an integer `version`.

A mutating transaction:

1. `SELECT ... FOR UPDATE` the order row, and the payment row when the rule depends on it.
2. Compare `version` with the version the caller read. On mismatch, return a conflict and stop.
3. Apply the state-machine and payment guards to the locked values, not to the values from the browser.
4. Update the row, increment `version`, and insert the event.
5. Commit.

Pickup and void of the same order contend on the payment row lock. One commits. The other re-reads and then fails its guard. The application does not swallow that failure.

Cash receipt uses the order total from the locked order items, not a total supplied by the browser. The submitted paise value must equal that total.

Idempotency keys for order placement will be unique per student. A retried place-order request with the same key returns the original order instead of inserting a second one. That constraint is part of the place-order transaction.

## Order ownership

- `orders.student_user_id` is set on insert and has no update path.
- Student queries include `student_user_id = :authenticated_user` and `canteen_id = :canteen`.
- Staff queries include `canteen_id` from the server-side assignment, not from an unchecked query parameter. A parameter may select among canteens the caller is actually assigned to.
- Deleting an order is not allowed. Terminal states stay readable.

## Safe QR pickup

QR pickup is not implemented in P001. When it is added, the rules are:

- The token is at least 256 bits from a cryptographic random generator.
- The database stores only a SHA-256 hash of the token. The raw token is returned once to the owning student.
- The QR payload is the opaque token, or a URL that contains only that token. It does not contain the order number, the student name, the email address, or the price.
- A token has an expiry and a consumed timestamp. Regenerating a token inserts a new hash and expires the previous row.
- The pickup transaction locks the order and the payment, requires fulfillment `READY` and payment `PAID`, requires a cashier or manager of that canteen, checks that the hash matches an unconsumed unexpired token, then sets `PICKED_UP` and consumed time together.
- Showing a QR code does not change payment status.
- Logs may contain the order id, actor id, and result. Logs must not contain the raw token.
- A guessed order id is not a pickup credential. Sequential ticket numbers may be printed for humans and are not authorization secrets.

### Pickup and notifications

`pickup_tokens` stores `token_hash`, order id, expires at, and consumed at. It does not store the raw token.

`notification_attempts` stores channel (`IN_APP` or `WEB_PUSH`), status (`PENDING`, `SENT`, or `FAILED`), and provider detail. Its status is not a column on `orders` or `payments`.

`push_subscriptions` stores the browser subscription for VAPID delivery. P001 does not create this table and does not generate VAPID keys.

### Audit

`audit_log` is insert-only: actor, canteen, action, target table, target id, reason, and a JSON object of non-secret details. Passwords, raw tokens, and connection strings are not valid details.

- `pickup_tokens (token_hash)` unique
- `menu_items (canteen_id, is_published)`

## Migration policy

A phase that introduces a table adds one Alembic revision reviewed with the code that writes it. Autogenerate is a draft. Money columns, check constraints, and unique partial indexes are confirmed by hand. Downgrades are written for schema changes that can be reversed without deleting recorded payments. A revision that would drop `payment_events` or `audit_log` is not an acceptable downgrade once those tables contain pilot data.
