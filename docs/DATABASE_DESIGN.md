# Database design

PostgreSQL 16 is the system of record. Migration `0001_baseline` creates no tables. Migration `0002_identity` creates the identity tables. Migration `0003_menu_ordering` creates the menu, station, daily stock, order, payment, and idempotency tables. Migration `0004_kitchen_queue` adds preparation tasks. Migration `0005_cash_pickup_notifications` adds cash, pickup and notification tables. Forecast tables are still only a target.

Redis is not a system of record. It is the Celery broker. Later short-lived coordination may use it. Orders and payments are never stored only in Redis.

## Conventions

- Primary keys are UUIDs generated by the database.
- Timestamps are `timestamptz` and stored in UTC.
- Operational rows include `canteen_id` even while the pilot has one canteen.
- Money columns are `bigint` paise. Names end in `_paise`. They are not `float`, `double precision`, or unscaled `numeric`.
- Status columns are text with a check constraint that matches the documented states.
- Updates that change an order or a payment also insert an event row in the same transaction.
- Foreign keys are indexed. The column that is filtered most often in a composite key comes first.

## Transaction boundaries

Each boundary is one database transaction. The service commits once at the end. A failure rolls the whole boundary back.

| Boundary | Writes | Must not do |
| --- | --- | --- |
| Place order | Order, items, PENDING payment, PLACED event, stock reservation | Mark PAID or PICKED_UP |
| Fulfillment transition | Order status, version, fulfillment event | Touch payment status |
| Cash receipt | Payment PENDING to PAID, payment event, audit | Set PICKED_UP or notification status |
| Pickup | Order READY to PICKED_UP, token consumed, fulfillment event, audit | Change the amount or create the payment |
| Void | Payment PAID to VOIDED, payment event, audit | Delete the PAID event or rewrite a PICKED_UP order into READY |
| Staff change | Assignment and audit | Modify orders |
| Notification attempt | Notification row only | Modify order or payment |

Readiness probes (`SELECT 1`, `PING`) are not domain transactions.

## Concurrency

Order and payment rows carry an integer `version`.

A mutating transaction:

1. `SELECT ... FOR UPDATE` the order row, and the payment row when the rule depends on it.
2. Compare `version` with the version the caller read. On mismatch, return a conflict and stop.
3. Apply the state-machine and payment guards to the locked values, not to the values from the browser.
4. Update the row, increment `version`, and insert the event.
5. Commit.

Pickup and void of the same order contend on the payment row lock. One commits. The other re-reads and then fails its guard. The application does not swallow that failure.

Cash receipt uses the order total from the locked order items, not a total supplied by the browser. The submitted paise value must equal that total.

Idempotency keys for order placement will be unique per student. A retried place-order request with the same key returns the original order instead of inserting a second one. That constraint is part of the place-order transaction.

## Order ownership

- `orders.student_user_id` is set on insert and has no update path.
- Student queries include `student_user_id = :authenticated_user` and `canteen_id = :canteen`.
- Staff queries include `canteen_id` from the server-side assignment, not from an unchecked query parameter. A parameter may select among canteens the caller is actually assigned to.
- Deleting an order is not allowed. Terminal states stay readable.

## Safe QR pickup

QR pickup is implemented in P005 (`0005_cash_pickup_notifications`, see `P005_QR_SECURITY.md`). The rules, with the P005 differences noted:

- The token is at least 256 bits from a cryptographic random generator.
- The database stores only a hash of the token. P005 uses HMAC-SHA256 with a server key (`PICKUP_HASH_KEY`) rather than a bare SHA-256, and also stores a keyed hash of the manual fallback code. The raw token is returned once to the owning student.
- The QR payload is the opaque token, or a URL that contains only that token. It does not contain the order number, the student name, the email address, or the price.
- A token has an expiry and a consumed timestamp. Regenerating a token inserts a new hash and expires the previous row.
- The pickup transaction locks the order and the payment, requires fulfillment `READY` and payment `PAID`, requires a cashier or manager of that canteen, checks that the hash matches an unconsumed unexpired token, then sets `PICKED_UP` and consumed time together.
- Showing a QR code does not change payment status.
- Logs may contain the order id, actor id, and result. Logs must not contain the raw token.
- A guessed order id is not a pickup credential. Sequential ticket numbers may be printed for humans and are not authorization secrets.

### Pickup and notifications

`pickup_tokens` stores `token_hash`, order id, expires at, and consumed at. It does not store the raw token.

`notification_attempts` stores channel (`IN_APP` or `WEB_PUSH`), status (`PENDING`, `SENT`, or `FAILED`), and provider detail. Its status is not a column on `orders` or `payments`.

`push_subscriptions` stores the browser subscription for VAPID delivery. P001 does not create this table and does not generate VAPID keys.

### Audit

`audit_log` is insert-only: actor, canteen, action, target table, target id, reason, and a JSON object of non-secret details. Passwords, raw tokens, and connection strings are not valid details.

## Implemented kitchen queue (`0004_kitchen_queue`)

`orders` gained nullable `accepted_at`, `ready_at`, `eta_ready_at`, `eta_earliest_at`, `eta_latest_at`, and `eta_computed_at`, plus `eta_version`, `eta_overdue`, and `eta_blocked`. Timestamps are `timestamptz`.

`preparation_tasks` has a UUID primary key and foreign keys to `orders`, `order_items`, `canteens`, `kitchen_stations`, and `users` (`started_by`, `completed_by`). Unique `(order_item_id, unit_index)`. Status is `QUEUED`, `IN_PROGRESS`, `DONE`, or `CANCELLED`. Duration is 30–7200 seconds. Indexes cover `order_id`, `(kitchen_station_id, status)`, and `(canteen_id, status)`. Station name, item name, and expected duration are copied onto the task.

The earlier target names (`stations.concurrent_capacity`, `fulfillment_status`, `public_number`) are the design vocabulary. The migrated tables use `kitchen_stations.parallel_capacity`, `orders.status`, and `orders.ticket_number`.

## Implemented cash, pickup, and notifications (`0005_cash_pickup_notifications`)

`orders` gained `picked_up_at` and `picked_up_by`. `order_payments` gained `paid_at` and `paid_by`. (The migrated payment table is `order_payments`. The target name `payments` is design vocabulary.) A reversal clears `paid_at` and `paid_by` and returns the status to `PENDING`. The `VOIDED` status and the `voided_*` columns in the target design are not used.

| Table | Purpose and key constraints |
| --- | --- |
| `cash_receipts` | One row per cash confirmation. `receipt_no` from `cash_receipt_no_seq` (unique, shown as `CR-000123`). Unique `(payment_id, attempt_no)` and `(payment_id, idempotency_key)`. `amount_paise >= 0`. Keeps cashier, `received_at`, ticket number. Append-only |
| `cash_reversals` | One row per reversed receipt (unique `receipt_id`). `kind` is `CASH_RETURNED` or `ERRONEOUS_ENTRY`. `reason` is 5 to 300 characters. Keeps the manager and time. Append-only |
| `pickup_credentials` | `token_hash` (unique) and `code_hash`, never the raw values. `expires_at > created_at`. Partial unique index `uq_pickup_credentials_one_active` allows one live credential per order. Records revocation and redemption (who, when, key) |
| `pickup_events` | `ISSUED`, `VERIFIED`, `VERIFY_REJECTED`, `REDEEMED`, `REDEEM_REJECTED` and `REVOKED`, with actor and outcome. Append-only |
| `push_subscriptions` | Unique `endpoint_hash`. Endpoint, `p256dh` and `auth` are Fernet-encrypted. `enabled`, `disabled_reason`, last status and failure count |
| `notifications` | In-app messages. Unique `(user_id, dedupe_key)` so a retry cannot duplicate one |
| `notification_outbox` | Written in the READY transaction. Unique `event_key` (`ORDER_READY:{order}:{version}`). Status `PENDING` or `DONE` plus a result. `next_attempt_at` and `locked_until` for claiming |
| `push_deliveries` | One row per event and device (unique). Status `PENDING`, `ACCEPTED`, `REJECTED`, `GONE`, `FAILED` or `SKIPPED`. Attempts, response status, latency, error code, transport |

`bowlbyte_forbid_ledger_change()` is a trigger function attached to `cash_receipts`, `cash_reversals` and `pickup_events`. It rejects `UPDATE` and `DELETE`. Foreign keys from the three ledger tables to orders, users and canteens use no cascade, so history cannot disappear with a parent. The push and notification tables (`push_subscriptions`, `notifications`, `notification_outbox`, `push_deliveries`) cascade from their user, subscription or outbox row, because they are delivery state rather than a financial record.

Lock order for the new transactions: order, then payment, then receipt or credential. Cash confirmation, reversal and redemption all follow it.

## Pickup holds (`0007_pickup_holds`)

`canteens.pickup_hold_minutes` defaults to 30 and must be between 5 and 180. When an order becomes READY, `orders.pickup_hold_until` is set from that policy. The 10-minute QR lifetime is a different column on `pickup_credentials` and is not this deadline.

`UNCLAIMED` was already allowed by `ck_orders_status`. The sweep sets that status, `unclaimed_at`, and an `order_hold_events` row. It does not write cash, waste, or stock. A manager extension sets the status back to READY with a new deadline. An old QR still fails the READY check until a new credential is issued.

## Implemented food intelligence (`0006_food_intelligence`)

Production batches are not `daily_stock`. Recording a batch does not change saleable stock. Online pickups are not added into the batch equation. Demo demand lives only in `demo_demand_days` and is not an order or a cash receipt.

| Table | Purpose and key constraints |
| --- | --- |
| `food_production_batches` | Prepared food. `produced = served_counter + remaining + discarded`. Unique canteen batch code and idempotency key. Source `REAL` or `DEMO` |
| `production_quantity_events` | Append-only `OPEN`, `SERVE_COUNTER`, `DISCARD`, `CORRECT` |
| `food_waste_records` | A recorded discard. Reasons `UNSOLD`, `PREPARATION_ERROR`, `QUALITY_REJECTION`, `SPOILAGE`, `OTHER`. Optional batch |
| `canteen_closures` | Unique `(canteen_id, service_date)`. A closed day is not a zero-sales day |
| `demo_demand_days` | Seeded synthetic history. Unique `(canteen_id, menu_item_id, service_date)` |
| `forecast_jobs` | `PENDING`, `RUNNING`, `SUCCEEDED`, `FAILED`. Unique canteen idempotency key |
| `forecasting_models` | `SEASONAL_NAIVE` or `HIST_GRADIENT_BOOSTING`. Status `CANDIDATE`, `ACTIVE`, `REJECTED`, `FAILED` |
| `model_evaluations` | `VALIDATION` or `HOLDOUT`. MAE and WAPE stored as milli-units. WAPE is null when undefined |
| `demand_forecast_runs` | Horizon 1 or 7. Status `COMPLETE` or `INSUFFICIENT_DATA`. Method `BASELINE` or `ML` |
| `demand_forecast_values` | One predicted quantity per item and date, with a labelled range |
| `preparation_plans` | `DRAFT`, `REVIEWED`, `APPROVED`, `REJECTED`, `SUPERSEDED` |
| `preparation_plan_items` | The quantities and the explanation. An override is a separate column |
| `preparation_plan_events` | `CREATED`, `ADJUSTED`, `APPROVED`, `REJECTED`, `SUPERSEDED` |

Batch codes come from `production_batch_no_seq`. Model files, when an ML candidate is fit, are written under `var/forecast_artifacts` and checked by SHA-256. They are not database blobs and they are not loaded from a client-supplied path.

## Migration policy

A phase that introduces a table adds one Alembic revision reviewed with the code that writes it. Autogenerate is a draft. Money columns, check constraints, and unique partial indexes are confirmed by hand. Downgrades are written for schema changes that can be reversed without deleting recorded payments. A revision that would drop `payment_events` or `audit_log` is not an acceptable downgrade once those tables contain pilot data.
